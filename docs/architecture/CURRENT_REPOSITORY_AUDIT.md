## 3. Architectural problems

1. **The `platform/poc/` name is now false.** It contains a tested commerce system with
   migrations, an audit trail and a mutation harness. Calling it a proof of concept invites
   someone to treat verified code as disposable.
2. **No application separation.** Web, admin and mobile are siblings *inside the backend's
   parent*. `apps/admin/index.html` reaches up and across into `../storefront/styles.css`, so the
   two clients cannot be built, deployed or owned independently.
3. **Duplicate ownership of the same concept.** Two admin authentication models on adjacent
   paths (legacy `X-Admin-Token` at `/api/v1/admin/products` versus role-based sessions at
   `/api/v1/admin/catalog/products`), and two catalogue sources (JSON fixture versus database).
   Both are deliberate and documented, but the layout gives no hint which is authoritative.
4. **No authoritative contract location.** `openapi.json` sits under the backend's own docs, so
   mobile and web have no natural place to consume it and will drift.
5. **Evidence, documentation and source are interleaved.** `platform/poc/docs/` sits beside a
   repository-level `docs/`, and there is no obvious home for command transcripts.
6. **Infrastructure is mixed into application source.** `docker-compose.yml`, `Makefile`,
   `.env.example` and `.dockerignore` all live inside the application directory.
