## 1. One-agent responsibility model

The agent performs all knowledge-work roles on its side: planning,
research, structured analysis, artifact creation, review, testing,
documentation and dependency management. It must not confuse broad
competence with physical or legal authority.

| **Boundary**                   | **Rule**                                                                                                                                                    |
|--------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Agent can complete             | Plans, research dossiers, specifications, structured data, brand/technical files, code, tests, reports, checklists, validation, documentation and handoffs. |
| Requires human verification    | Business/founder approval, creative approval, physical sample/fit/QC decisions, real operational UAT and go/no-go authority.                                |
| Requires external verification | Legal/tax/customs advice, trademark clearance, laboratory/factory audit, registrations, payment/carrier/app-store approval and real shipment evidence.      |
| Never acceptable               | Invented evidence, implied approval, synthetic results represented as market truth, or “done” without artifact and acceptance proof.                        |

## 2. Evidence and completion protocol

| **Status**          | **Required interpretation**                                                      |
|---------------------|----------------------------------------------------------------------------------|
| DRAFT               | Artifact exists; validation not completed.                                       |
| SELF-VALIDATED      | Agent passed the book checklist and consistency review.                          |
| AUTOMATED-TESTED    | Machine checks passed with command/log evidence.                                 |
| HUMAN-VERIFIED      | Named accountable person reviewed the defined scope.                             |
| EXTERNALLY-VERIFIED | Qualified provider, authority, factory, laboratory or adviser supplied evidence. |
| BLOCKED             | Mandatory dependency is missing; owner, impact and fallback recorded.            |
| REJECTED            | Acceptance failed; correction is tracked.                                        |

## 4. Mandatory first execution

1\. Read this entire book and the shared interface contract.

2\. Inspect all provided files, repositories, templates and prior
outputs.

3\. Initialize every register and the folder structure.

4\. Publish an intake report separating verified facts, assumptions,
missing evidence and contradictions.

5\. Run all available automated tests/validators and preserve exact
output.

6\. Create the gate roadmap and a detailed two-week backlog.

7\. Issue the first dependency templates and requests to the other side.

8\. Start the highest-value non-blocked work immediately.

## 5. Work-package operating algorithm

1\. Confirm objective, definition of done and target gate.

2\. Classify each prerequisite: available, assumed, requested or
blocking.

3\. Create task/artifact IDs and acceptance criteria.

4\. Produce the required artifact in its specified format.

5\. Run self-checks and automated validation.

6\. Reconcile against cross-team contracts and source-of-truth owners.

7\. Request human/external verification where necessary.

8\. Create a formal handoff and process the receiver response.

9\. Update evidence, risk, decision and deliverable registers.

10\. Close only after required evidence or explicit risk acceptance.

## 6. Handoff envelope

- Handoff ID, sender/receiver and date

- Related work-package/artifact IDs

- Purpose and consuming workflow

- Payload files/data and schema/version

- Confirmed facts, assumptions and questions

- Acceptance criteria and validation steps

- Need-by gate/date, delay impact and safe fallback

- Change-control and superseded version

- Receiver result: accepted, conditionally accepted or rejected

## 7. Gate control

| **Gate** | **Exit condition**                                                                |
|----------|-----------------------------------------------------------------------------------|
| G0       | Workspace, registers, ownership and first backlog initialized.                    |
| G1       | Market/product strategy and architecture/data contracts align.                    |
| G2       | One product has physical/evidence-backed truth and a complete digital record.     |
| G3       | Staging supports the complete sellable and reversible commerce journey.           |
| G4       | Operational beta, real package flow, UAT, finance and security controls pass.     |
| G5       | Production, registrations, batch release, monitoring and launch dossier approved. |
| G6       | Scale/stop decisions use actual customer, economics and reliability evidence.     |

## 8. Required cycle report

1\. Current gate and objective

2\. Completed artifacts with ID/version/status/evidence

3\. Validation commands/checklists and results

4\. Incoming handoffs accepted/rejected

5\. Outgoing handoffs and exact requests

6\. Blockers, risks and safe fallback

7\. Decisions with options/recommendation/deadline

8\. Next executable tasks

9\. Objective readiness by gate criteria

## 9. Definition of market-ready

- \[ \] One real product is traceable from source evidence to digital
  listing, order and post-order operations.

- \[ \] Product facts, claims, prices, stock and policies reconcile.

- \[ \] Critical success/failure/recovery scenarios pass.

- \[ \] External approvals are evidenced rather than inferred.

- \[ \] Test shipment/return and finance reconciliation are possible.

- \[ \] Security/privacy/accessibility and operations controls are
  tested.

- \[ \] Deployment, rollback, backup restore, monitoring and incident
  response are rehearsed.

- \[ \] Open risks have named owners and explicit go/no-go treatment.

# PART I — Vision, scope and measurable success

## 1. Product and company vision

Build a premium fashion brand whose defensible core is the combination
of credible Egyptian cotton sourcing, modern Eastern visual language,
disciplined quality, transparent product data and a digital customer
experience designed for Europe.

### 1.1 Initial market hypothesis

| **Dimension** | **Working assumption**                                                                                           | **What must validate it**                                                 |
|---------------|------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------|
| Customer      | Style-conscious European and diaspora customers seeking premium, culturally distinctive apparel.                 | Interviews, waitlist conversion, paid test campaigns and repeat purchase. |
| Offer         | Small capsule collections: T-shirts, shirts and selected modest/elevated pieces such as modern abayas.           | Sample feedback, return reasons, fit testing and margin.                  |
| Positioning   | Premium accessible, not luxury theatre and not low-cost basics.                                                  | Willingness-to-pay tests and competitor price mapping.                    |
| Proof         | 100% cotton claims supported by supplier documents and independent tests where appropriate.                      | Batch traceability, fibre composition evidence and QC records.            |
| Channel       | Web-first Europe launch; mobile beta follows proven usage and retention.                                         | Web conversion, customer requests and mobile repeat-use case.             |
| Supply model  | Manufacture and package in Egypt; import in controlled batches to an EU fulfilment point for the initial launch. | Landed-cost comparison against direct shipment per order.                 |

| **Recommended launch model:** Import a controlled batch into one EU fulfilment location and sell from an EU merchant entity. Direct-to-consumer shipping from Egypt for every order can create slow delivery, inconsistent duties, expensive returns and a weak customer experience. Keep it as an exception or test lane, not the default. |

## 13. Gate criteria

| **Gate**            | **Must be true**                                                                              | **Stop or pivot when**                                         |
|---------------------|-----------------------------------------------------------------------------------------------|----------------------------------------------------------------|
| G0 — Commit         | Founder/IP agreement, named owners and spending limit.                                        | Ownership or decision rights remain vague.                     |
| G1 — Product thesis | Customer problem, capsule and price hypothesis supported by interviews/tests.                 | Offer is only personal taste with no target customer evidence. |
| G2 — Makeability    | Factory can reproduce approved sample within quality, lead time and target cost.              | Sample variation or MOQ destroys economics.                    |
| G3 — Importability  | Classification/origin, importer, EORI/VAT, packaging and product compliance path reviewed.    | Nobody accepts importer/product-safety responsibility.         |
| G4 — MVP build      | Data contract frozen for launch scope and operational processes testable.                     | Products, sizes, prices or fulfilment remain unknown.          |
| G5 — Launch         | Critical path tests, legal review, monitoring, backup, support and stock reconciliation pass. | Payment/order/return flow cannot be recovered manually.        |
| G6 — Scale          | Demand, repeat rate and contribution margin justify more inventory/features.                  | Growth hides negative unit economics or high returns.          |

| Shared channel API    | The Expo mobile source consumes the same product endpoint.                                   |
| AI pattern            | A deterministic recommender ranks only active in-budget products and explains the selection. |
| Operational API       | Quote endpoint verifies SKU and stock and returns a transparent PoC total.                   |

## 17. PoC setup and demo

> 1\. Install Docker Desktop or Docker Engine with the Compose plugin.
>
> 2\. Extract the PoC package and copy .env.example to .env.
>
> 3\. Change ADMIN_API_TOKEN before sharing the environment.
>
> 4\. Run: docker compose up --build
>
> 5\. Open the storefront at http://localhost:3000 and API documentation
> at http://localhost:8000/docs.
>
> 6\. Demonstrate catalog, stock, stylist and quote scenarios using the
> README demo script.
>
> 7\. For mobile, set EXPO_PUBLIC_API_BASE for emulator/phone, install
> dependencies and run npx expo start.

| **PoC limitation:** It does not collect live payment, calculate VAT/customs, persist transactional orders, reserve inventory atomically, print carrier labels or contain final legal text. Exposing it as a live shop would be irresponsible. |

## 19. Architecture principles

- Web-first launch; mobile is a separate value decision, not a vanity
  requirement.

- Modular monolith before microservices. Split only where team scale,
  reliability or load provides evidence.

- Managed services before Kubernetes. Operational complexity is a cost,
  not a badge.

- Provider-hosted/tokenized payment UI; never build card handling from
  scratch.

- PostgreSQL is the transactional source of truth; analytics copies do
